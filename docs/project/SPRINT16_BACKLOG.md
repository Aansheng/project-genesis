## WO-S16-001 — Targeted Gameplay Rule Reconciliation Across World Evolution

Status: DONE. Generated by the completed `SPRINT16_DISCOVERY` after the
Human/CTO decision on 2026-08-24; implemented and Product Verified on
2026-08-24.

Architecture before: v1.154.

Architecture expected after: v1.155.

Architecture actual after: v1.155. ADR-0269 records the accepted
provider-independent reconciliation boundary.

### Objective

After an applied semantic World Evolution delta, produce a new current
world-bound `GameplayRuleSet` from:

`Current Semantic World + Current GameplaySpecification + Current GameplayRuleSet
+ Applied Semantic Delta + Genesis Gameplay Capability Catalog`

The result must preserve unaffected rules, revalidate affected rules, remove
invalid or dangling exact references, and deterministically rebuild affected
known rules through the existing `GameplayRuleBuilder` path.

### Acceptance boundary

- Unrelated semantic evolution preserves executable rules and binds the new
  semantic revision.
- Targeted entity/category/archetype changes affect only actually impacted
  rules.
- Removed exact targets cannot leave executable dangling rules.
- Affected known rules are revalidated or deterministically rebuilt; rules that
  cannot be resolved are removed or visibly deferred, never falsely executed.
- A semantic revision change alone never globally disables the RuleSet.
- Provider/AI is not called for deterministically reconcilable changes.
- Gameplay continues in the same Runtime/session without full Runtime,
  Renderer, or current-world rebuild.
- World A rules/results cannot affect World B.
- Observatory separates reconciliation facts from Runtime execution facts.

### Authority and constraints

`GameplaySpecification` remains design-intent authority. The reconciled
`GameplayRuleSet` remains executable rule-plan authority. Runtime remains
execution/state authority. Web/Pinia/Observatory remain projections.

Do not add `GameplayRuleManager`, a generic workflow engine, event sourcing, a
second gameplay authority, entity-ID-prefix archetype inference, arbitrary
code/eval/scripts, broad World Evolution infrastructure, or progression and
failure systems. AI regeneration is a fallback only for genuinely new or
ambiguous intent that cannot be derived from current deterministic inputs.

### Required evidence

Focused Shared/AI/Runtime/Web tests, affected-package regressions, TypeScript,
ESLint, Web build when integration changes, and one manual Studio session
covering unrelated preservation, targeted reconciliation/removal, continued
movement/jump and an unaffected mechanic, truthful RuleSet/Runtime/Observatory
state, same-session continuity, World A/B isolation, and clean browser logs.

After this bounded bridge, Next-Work Discovery identified the missing
Runtime-owned numeric state behind the already-described `CHANGE_NUMERIC_STATE`
action as the smallest Part 2 bottleneck. Level thresholds, level-up, skills,
modifiers, spawning, and waves are not pre-planned.

## Completion evidence

- Shared/AI deterministic reconciliation preserves unaffected rules, advances
  the current semantic revision, rebuilds/removes targeted rules, and exposes
  immutable reconciliation facts.
- Runtime keeps the same execution loop and session active while the current
  RuleSet advances; no full Runtime/Renderer/world rebuild occurs.
- Web commits semantic state only with a reconciled current RuleSet and records
  separate reconciliation stages/events in Observatory projections.
- Focused and affected-package tests, TypeScript, ESLint, and Web build passed.
- Manual Studio verification passed on 2026-08-24, including targeted and
  unrelated evolution, the same-session Running movement/jump control surface,
  unaffected gameplay, truthful Observatory state, and clean browser logs;
  Runtime/AI regression tests cover authoritative movement/jump continuity and
  World A/B isolation.

## WO-S16-002 — First Generic Progression Loop: Authoritative Numeric State

Status: DONE. Generated by the CONTINUE Next-Work Discovery on 2026-08-24;
implemented and Product Verified on 2026-08-24.

Architecture before: v1.155.

Architecture expected after: v1.156.

Architecture actual after: v1.156. ADR-0270 records the accepted
Runtime-owned numeric progression boundary.

### Objective

Execute one validated `CHANGE_NUMERIC_STATE` action from the existing
GameplayEvent → GameplayRule path into a small Runtime-owned immutable numeric
progression state. `experience` is the first measured state key/use case.

### Acceptance boundary

- Current supported rules can commit finite additive numeric deltas.
- Empty keys, non-finite amounts, missing state, stale bindings, and failed
  later actions do not commit.
- State accumulates deterministically, remains across semantic revision changes,
  and resets on world/session replacement.
- Renderer and Observatory expose numeric progression separately from raw facts,
  rule results, and Runtime World mutations.
- `NUMBER_COMPARE`, thresholds, level-up, skills, modifiers, score policy,
  timers, spawns, waves, and Survivor-specific behavior remain deferred.

### Authority and constraints

Runtime owns committed progression state. GameplaySpecification remains intent;
GameplayRuleSet remains executable plan; Web/Pinia/Observatory are projections.
Do not add `SurvivorRuntime`, `XPManager`, `ProgressionManager`, generic
workflow infrastructure, generated code, or offline World Evolution fallback.

### Completion evidence

The existing Runtime path now carries a supported finite additive
`CHANGE_NUMERIC_STATE` action from `GameplayEvent` → `GameplayRule` → immutable
Runtime-owned keyed numeric state. The deterministic platformer collect-reward
rule removes the item and commits `experience +1`; the state is forwarded by
the existing Renderer loop and projected separately by Observatory.

Focused and affected-package verification passed: Shared 207 tests, AI 9,402,
Runtime 689, Renderer 485, and Web 3,528. Direct TypeScript checks, package
ESLint (0 errors; existing warnings remain), and the Web production build
passed. The root Turbo typecheck wrapper remains blocked by the managed
environment's missing TLS/keychain access.

Manual Studio verification on 2026-08-24 used the real local Studio and a
temporary localhost-only structured candidate gateway. In `world-3`, collecting
the item showed `经验值: 1`; a theme evolution applied while the same Game
Runtime/session remained mounted, and Observatory still showed `经验值: 1`.
Creating `world-4` showed `经验值: Unavailable`, proving world/session reset.
Final browser diagnostics contained no warning or error entries.
