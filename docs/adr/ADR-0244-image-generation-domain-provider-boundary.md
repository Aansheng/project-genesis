# ADR-0244: Image Generation Domain & Provider Boundary

**Status:** Accepted  
**Date:** 2026-08-18  
**Work Order:** WO-S13-007  
**Architecture Version:** v1.130 → v1.131

## Context

Genesis has a provider-independent visual design and asset pipeline, but no
domain contract for producing an asset. A future provider must support more
than text-to-image without coupling shared code to a vendor, Pixi, Runtime, or
browser UI.

## Decision

`@genesis/shared` owns `ImageGenerationRequest`, `ImageGenerationResult`,
`GeneratedImageAsset`, `ImageGenerationProvider`, and
`ImageGenerationOperation`. One request carries a first-class mode for
text-to-image, image-to-image, edit, or reference-guided generation. It keeps
the canonical `assetId`, prompt, existing `AssetVisualContext`, optional source
and reference asset identities, and small vendor-neutral output constraints.

Providers report capabilities through `supports(mode)` and must represent an
unsupported mode explicitly. Failures use a small typed taxonomy. Operations
expose only request facts, output metadata, status, failure, and future static
or primitive fallback; secrets and hidden reasoning are never part of the
contract.

Generated resources remain opaque and are not sent to Pixi directly. The
future path is generated artifact storage/publication → `AssetManifest` →
`AssetStore` → renderer. The current static catalog and primitive fallback are
unchanged.

## Consequences

- A later image provider can be injected without changing the semantic asset
  model or renderer.
- All four planned modes are representable now, while only future providers
  decide which modes they execute.
- Generated bytes, persistence, manifest publication, Observatory UI, and
  provider SDK integration remain separate follow-up work.
